# Stage 3: demand-aware polling (issue #17)

**Status: implemented behind an option that defaults OFF; qualified offline (unit tests + a 48 h virtual-time simulation of the real scheduler against a fake cloud and a model of Package 19) and in Docker against stub services (§7). NOT deployed, physical commissioning NOT_RUN, not approved for release or activation (see §10), no add-on version bump, not combined with PR #24.** Every request count below is a model result calibrated to the measured system (today's idle 672/day was reproduced). They are **not vendor quotas**, and idle figures are **not ownership-ON budgets** (§5).

## 1. Problem
At `poll_interval: 180` with Package 19's pre-cycle refresh the bridge sends ~672 requests per UTC day (28/h); the vendor answered `Daily request limit exceeded` after 469 recorded requests (435 status + 34 auth) on 14 and 15 November. Requirements that must not change: source telemetry ≤ 120 s old when Package 19 evaluates it, device offline after a **fixed 300 s** without a successful poll, command confirmation (20 s for 60 s), safe handback, fail-closed behaviour.

## 2. Where the traffic goes (installed 1.9.0)
Per five-minute cycle: Package 19 publishes `P/<sn>/refresh` at `:x4:30` (primary) and `:x4:48` (retry only if no healthy poll since `:20`); the bridge serves each ~2.2 s later; the loop then waits a **full** `poll_interval` after *every* cycle, so a timed poll lands 180 s after the demand poll. Result: **2 `/status` per cycle = 576/day**, plus 48 tokens/day (1,800 s life) × (refresh + replayed `/status`) = **+96** → 672. **Redundant when healthy:** the timed poll (~288/day). The demand poll is the only request inside the 120 s window.

## 3. Design (all behind `demand_aware_polling`, default false)
Applies only when **(i)** the option is on, **(ii)** `poll_interval` > 120 (Package 19 only requests refreshes above 120; otherwise ignored, logged, legacy), **(iii)** refresh requests were seen in the last 660 s (else legacy cadence returns, so a stopped Package 19 cannot erode the 300 s bound).
1. **Reuse is granted by explicit intent only.** Package 19's pre-cycle automation publishes the payload **`precycle`**; a requested refresh with exactly that payload needs no request when the last poll is healthy and ≤ `DEMAND_REUSE_MAX_AGE_S` = 80 s old. **Everything else is a forced refresh that always gets a real poll** (subject only to the existing 10 s attempt coalescing): the handback script's and the HA-start recovery's plain `"1"`, manual publishes, and any unknown, empty, differently-cased, whitespace-padded or undecodable payload. When several requests for one device are pending, forced intent wins in either arrival order and a marked request never upgrades a forced one. **Arrival time is never used**: an earlier revision inferred origin from the 266–299 s phase of the five-minute grid and was shown unsafe (§6). Also never reused: in a confirmation window, after a failure, during/after quota, before the first poll, or while the observed setpoint is ≥ 65 °C (data-quality choice for owned boosts, ~+2–5 requests/day).
2. **Deadline poll.** After every cycle the loop waits until `last_success + 300 − 10 s` instead of a fixed interval. A failed deadline poll gets one 5 s retry when it still fits; otherwise one 20 s recovery retry (once per success stamp), then the legacy interval. Backoff, unverified recovery and the 20 s confirmation cadence are untouched.
3. Energy-integration cap floors at 300 s; the proactive-refresh margin follows the 290 s wake gap (350 s); diagnostics publish `demand_aware_polling` and `demand_refresh {served, reused, marked, forced}`.
Result healthy with a marked Package 19: 36 demand-served + 290 deadline polls/day = **1.132 polls/cycle**. With Package 19 unchanged (plain `"1"`): no reuse, the timed poll is still replaced by the deadline poll: ≈ 529/day idle.

## 4. Timing against Package 19 (source read, simulator models it)
* Template `binary_sensor.ems_hws_current_action_available` (ownership off) tests `poll_status == ok`, failures == 0 and `now() − last_successful_poll ≤ 120` (1 s resolution) **at render time**: HA re-renders on dependency changes and each minute (`now()`), so the EMHASS snapshot (~T+3 s) and the translation event (T+8…11 s) see the state rendered at the `:00` tick unless a dependency changed since.
* Worst-case age with a marked Package 19: ≈ 80 + 9.8 = **90 s** at T (measured max 86 s), **96 s** at the translation event: 24 s inside the gate. A threshold of 110 s breaches it (53 cycles > 120 s); 100 s leaves 5 s.
* Handback script: its `refresh` (plain `"1"`) is never reused, so it waits for and gets a real poll exactly as on 1.9.0; acquisition uses telemetry ≤ 96 s old instead of ≤ 39 s.
* Ownership ON: `available` is just `heating == on` (no age test). A physical change is seen by the first EMHASS read after it: mean 178 s → 200 s (+22 s), next cycle 90.7 % → 83.5 %. A mid-boost Eco switch still releases ownership with **no** command (identical to today); the 70 °C thermostat remains the physical limit.

Real boost days (recorder, 8/9/10 Nov) used 10/15/26 bridge commands; each costs ≈ 4.5 requests (POST + ≥ 3 confirmation polls), ≈ 13 per boost, in every configuration. **Only idle and light days meet 450; the idle figure is not an ownership-ON budget.** Proactive refresh alone saves 42/day (not 68).

### How a 27-command day exceeds the observed 469-attempt first-rejection count
Arithmetic: 419 idle + 27 × 4.5 ≈ 541 (marked) — above 469 by ≈ 70–76 (unmarked 646, DP-marked 510). The excess is consumed as idle polling continues after the boosts: with the observed profile (boosts 01:25–05:10 UTC, early in the UTC day) a hypothetical 468 cap is first hit at 19.7 h UTC (D) / 21.4 h (DP) / 12.6 h (1.9.0), **after** the handbacks, giving 2.6–4.3 h of telemetry blackout and no outstanding handback (ownership false, setpoint 58 °C at midnight). Stress case (same boosts 16.5 h later): 1.9.0 hits the cap before any boost starts (the template needs `poll_status == ok`, so nothing is acquired while limited), but **D/DP reach the cap inside the boost period** and leave an **outstanding handback for 3.2 h** (heater at 70 °C or at the TEMP 50 soft-stop setpoint) until the UTC reset and the next hourly probe. That is the real exposure introduced by lowering the request rate without budget awareness.

### Fail-closed safeguards protecting an outstanding handback (existing, verified in simulation)
Ownership is a durable `input_boolean` that survives HA restarts and is only cleared after a confirmed baseline restore (or a native non-Manual release); every wait in the handback script halts with ownership retained; during quota backoff the bridge refuses commands locally — never queued, never replayed after recovery — and sends only hourly probes (0 requests per failed attempt); the next EMHASS publication and every HA start retry the whole transaction with a fresh refresh; a native-mode change releases ownership without a command; no new acquisition can start while telemetry is stale/limited; the physical thermostat at 70 °C bounds the heater. Measured (one owned boost, then an obstacle): TEMP 50 never applied → 17 halted attempts × 5.0 requests, ownership retained 85 min (until the thermostat terminated at 70 °C), then ok; cloud unreachable 14 min → 3 halted × 2.0, 16 min; quota 90 min → 25 halted × 0.0, 126 min including the next probe. **Not provided:** a budget-aware acquisition gate (e.g. a Package 19 condition on the bridge's day counter leaving a reserve of ≳ 20 requests for refresh + TEMP 50 + baseline restore, threshold set by the operator because the vendor limit is unverified). Recommended as a separate change before ownership-ON use at these request levels; not implemented here.

## 6. Failure modes (all simulated with the real scheduler)
* **Origin classification (review finding, resolved).** At 9f60834 an ownership-ON handback or HA-start refresh (plain `"1"`, setpoint 58 °C, last poll 10–80 s old) arriving inside the 266–299 s phase was reused: **16 of 40 trials halted at the 20 s refresh wait** (0 of 40 on 1.9.0; 48 of 48 outside the phase ok). Explicit intent: 88/88 ok with Package 19 marked and with it unchanged; overlapping pre-cycle and handback requests within ±0.3 s of the pre-cycle arrivals, setpoint 50 °C after a soft stop, and HA-start recovery at six phases all ok.
* **Timeouts versus the 10 s margin.** Slow *successful* responses up to the 20 s HTTP timeout never publish offline (availability is evaluated only when idle or after a failure) although the success stamp can land past 300 s (gap 309 s at 19 s) — **not** a 300 s guarantee (a concurrent MQTT-thread publish is not modelled). A reset is absorbed by the 5 s retry. **Connect (5 s) and read (15 s) timeouts are not tolerated**: one offline publication, 15–25 s offline, recovered by the next attempt; today's 180 s cadence rides the same fault with no offline.
* **Failure tolerance, 8 seeds** (80 % reset / 12 % connect / 8 % read, 15 ms median post-stamp work), offline publications and seconds per 48 h: 1.5 % failure: today 0.5 / 3, poll_interval 300 8.9 / 56, **this PR 1.6 / 23**; 12.8 %: 12.5 / 339, 56.8 / 1,421, **28.8 / 725**. This PR is **less tolerant than today**. `OFFLINE_SAFETY_MARGIN_S` trades it against budget: idle 419 / 433 / 453 at margin 10 / 15 / 22 s (retained at 10 s for now).
* Outstanding handback obstacles, 48 h composite (failed refresh, transport failures, outage, HA restart, native pre-emption, quota window, missing demand): 0 stale cycles and 0 unexplained offline publications outside the injected windows; backoff and fail-closed commands as today.

**Verifier correction.** The first S/S0 run failed only the post-slow-window recovery assertion: the harness allowed 90 s, but after a failed cycle the bridge correctly waits the full 180 s poll interval (`_background_wait_s` shortens the wait to the 290 s deadline poll only once the last success is at least 289 s old, so it does not apply here). Both runs recovered 140 s after the slow window. Request-storm, re-login, quota-backoff, marked/forced and option-off assertions are unchanged. The failing first run is retained as historical evidence; the passing re-run is the qualification.

**What this does not show (NOT_RUN / unmodelled).** Physical commissioning (section 9), the real vendor cloud and quota, production Home Assistant and the real heater were **not** run: the Docker scenarios use stubs only. The Docker slow-response fault is injected early in a cycle (last success about 45 s old); a transport failure at the 290 s deadline poll itself is evidenced by simulation only (the 10 s margin does not tolerate the 5 s connect plus 15 s read timeouts: brief offline, fail closed, unchanged trade-off in section 6). A device in a failure state keeps the legacy interval for every device, so only a single-device installation is supported. The simulator models the cloud, latency/jitter, Package 19's template/translation/handback timing and a heater with simple physics; it does not model concurrent MQTT-thread publishes, the Supervisor, HA's real event ordering, or real post-stamp work. The vendor limit may not scale with request count at all (issue #17).

## 9. Supervised commissioning, rollback and the restart safety preflight
Merge ≠ release ≠ deploy: this PR does **not** bump the version; release separately (not combined with PR #24).
**Restart preflight — required before EVERY add-on restart, including enabling the option and any rollback; evaluate it at that moment, never assume the state from an earlier stage.** An add-on restart loses in-memory pending commands, starts the device offline until the first validated poll, and **HA's start-handback does not fire on an add-on restart**. Proceed only when all hold, read from HA/diagnostics now:
1. `input_boolean.ems_hws_ownership_active` is **off**. If on: do not restart; let the normal handback finish or follow the Package 19 runbook; if it cannot complete (quota, outage) leave the option as is — it does not weaken the handback path.
2. `script.hws_thermowatt_handback` is off, the translation automation is not mid-run (act 90–260 s after a cycle start), `sensor.p_deferrable0_state` is off.
3. No pending command: `sensor.outside_hws_hws_command_status` is `idle`/`confirmed`, outside a 60 s confirmation window.
4. Native baseline intact: `water_heater.hws_boiler_hws` is `Manual`, its setpoint equals `input_number.ems_hws_captured_baseline_setpoint_c` (or none captured), no owned boost.
5. `poll_status` ok, failures 0, no quota backoff, `last_successful_poll` fresh.
After the restart: availability online within 6 min, ownership still off, no unexpected commands, request rate as expected. A Supervisor option change restarts the add-on: same operation.
**Commissioning:** (1) install option off, 1 h at 24–30 requests/h; (2) preflight, option on, restart; with Package 19 unchanged expect `forced` counting every refresh and ≈ 22/h; after the marker is deployed expect `reused > 0` after 12 min; (3) ≥ 48 h **ownership OFF**: ≤ 430 requests per full UTC day once marked (≤ 540 unmarked), source age ≤ 120 s at every cycle outside quota windows (max ≤ 100 s at the translation event), zero unexplained offline and ≤ 5 offline events/48 h, transport failures ≤ 1.5 %, reuse:served ≥ 3:1 (marked), first-rejection count recorded; (4) only with separate approval and the budget-aware acquisition gate decision of §5, ownership ON for ≥ 3 boost days: every handback script run `ok` (traces show no refresh-wait timeout), all commands confirmed, telemetry age at the translation event while owned ≤ 60 s, requests/day ≤ idle + 5 × commands + 10 %.
**Rollback triggers:** one stale cycle outside a quota window, a handback halted at its refresh wait, a command not confirmed, an unexplained offline, > 460 requests on an idle day, reuse stuck at 0 with a marked Package 19. Rollback = **preflight, then** option false + restart (restores the 1.9.0 policy exactly; the HA store offers only higher versions, so a code rollback is a roll-forward release). Never roll back by restarting during an owned boost or a pending handback.
