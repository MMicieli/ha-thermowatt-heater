# Stage 3: demand-aware polling (issue #17)

**Status: implemented behind an option that defaults OFF; source-qualified offline only (unit tests + a 48 h virtual-time simulation of the real scheduler against a fake cloud and a model of Package 19). NOT deployed, NOT physically qualified, no add-on version bump, not combined with PR #24.** Every request count below is a model result calibrated to the measured system (today's idle 672/day was reproduced). They are **not vendor quotas**, and the idle figure is **not an ownership-ON budget** (see §5).

## 1. Problem
At `poll_interval: 180` with Package 19's pre-cycle refresh the bridge sends ~672 requests per UTC day (28/h); the vendor answered `Daily request limit exceeded` after 469 recorded requests (435 status + 34 auth) on 14 and 15 November. Requirements that must not change: source telemetry ≤ 120 s old when Package 19 evaluates it, device offline after a **fixed 300 s** without a successful poll, command confirmation (20 s for 60 s), safe handback, fail-closed behaviour.

## 2. Where the traffic goes (installed 1.9.0)
Per five-minute cycle: Package 19 publishes `P/<sn>/refresh` at `:x4:30` (primary) and `:x4:48` (retry only if no healthy poll since `:20`); the bridge serves each ~2.2 s later; the loop then waits a **full** `poll_interval` after *every* cycle, so a timed poll lands 180 s after the demand poll. Result: **2 `/status` per cycle = 576/day**, plus 48 tokens/day (1,800 s life) × (refresh + replayed `/status`) = **+96** → 672.
**Redundant when healthy:** the timed poll (~288/day). The demand poll is the only request inside the 120 s window.

## 3. Design (all behind `demand_aware_polling`, default false)
Applies only when **(i)** the option is on, **(ii)** `poll_interval` > 120 (Package 19 only requests refreshes above 120; otherwise ignored, logged, legacy), **(iii)** refresh requests were seen in the last 660 s (else legacy cadence returns, so a stopped Package 19 cannot erode the 300 s bound).
1. **Reuse, pre-cycle refreshes only.** A requested refresh needs no request when the last poll is healthy and ≤ `DEMAND_REUSE_MAX_AGE_S` = 80 s old, **and** it arrived 266–299 s into the five-minute grid (Package 19's `:x4:30`/`:x4:48` plus latency land at ~272 s and ~290 s). **Every other refresh is always served**: the handback script publishes `refresh` and waits ≤ 20 s for `last_successful_poll ≥ request − 10 s`, so reusing an old sample would starve it (found in review; PR head halted 18 of 24 simulated handbacks, see §6). Also never reused: in a confirmation window, after a failure, during/after quota, before the first poll, or while the observed setpoint is ≥ 65 °C (an owned TEMP 70 boost always gets fresh data; ~+2–5 requests/day).
2. **Deadline poll.** After every cycle the loop waits until `last_success + 300 − 10 s` instead of a fixed interval. A failed deadline poll gets one 5 s retry when it still fits; otherwise one 20 s recovery retry (`DEMAND_RECOVERY_RETRY_S`, once per success stamp), then the legacy interval. Backoff, unverified recovery and the 20 s confirmation cadence are untouched.
3. Energy-integration cap floors at 300 s; the proactive-refresh margin follows the 290 s wake gap (350 s); diagnostics publish `demand_aware_polling` and `demand_refresh {served, reused}`.
Result healthy: 36 demand-served + 290 deadline polls/day = **1.132 polls/cycle**.

## 4. Timing against Package 19 (source read, simulator models it)
* Template `binary_sensor.ems_hws_current_action_available` (ownership off) tests `poll_status == ok`, failures == 0 and `now() − last_successful_poll ≤ 120` (1 s resolution) **at render time**: HA re-renders on dependency changes and each minute (`now()`), so the EMHASS snapshot (~T+3 s) and the translation event (`ems_emhass_cycle_published`, historically T+8…11 s) see the state rendered at the `:00` tick unless a dependency changed since.
* Worst-case age: a reuse at `:30` (age ≤ 80 at T−28 s) would be ≤ 108 s at T, but whenever the success is older than `:20` HA also publishes the `:48` retry, which the bridge serves once its age exceeds 80 s: effective bound at T is ≈ 80 + 9.8 = **90 s** (measured max 86 s), and **96 s** when the translation event reads at T+10 s: 24 s inside the gate. A threshold of 110 s breaches it (53 cycles > 120 s at translation); 100 s leaves only 5 s.
* Handback script: refresh at T+10 s is outside the reuse phase, so the bridge polls (same as today); acquisition (`available`, no extra wait) uses telemetry ≤ 96 s old instead of ≤ 39 s.
* Ownership ON: `available` is just `heating == on` (no age test). A physical change (thermostat termination, app mode change) is seen by the first EMHASS read after it: mean 178 s → 200 s (+22 s), seen by the next cycle 90.7 % → 83.5 %, max 328 → 385 s. Native-mode guards re-read after the handback's fresh refresh, so a mid-boost Eco switch still releases ownership with **no** command (identical to today). The 70 °C thermostat remains the physical limit. A boost-specific faster policy is therefore a data-quality choice, not a safety need; the shipped setpoint ≥ 65 °C rule cuts max telemetry age while owned from 95 s to 48 s for +5 requests/day on the heaviest real day.

|---|---|---|---|---|
| Current 1.9.0 | 672 | 698 | 737 | 789 |
| + `proactive_token_refresh` | 630 | 656 | 695 | 747 |
| **This PR** | **419** | **448** | **488** | **545** |
| **This PR + proactive** | **384** | **413** | **453** | **510** |
Real boost days (recorder, 8/9/10 Nov) used 10/15/26 bridge commands; each command costs ≈ 4.5 requests (POST + ≥ 3 confirmation polls), ≈ 13 per boost. **Only idle and light days meet 450; the 418 idle figure must not be read as an ownership-ON budget**, and no cadence change can remove confirmation polling. Reserve under 450: ~6 commands/day (PR alone) or ~14 (with proactive refresh). Proactive refresh alone saves 42/day (96 reactive − ~53 proactive overhead), not 68; with demand-aware cadence it renews earlier (350 s margin) and saves ~35.

## 6. Failure modes (all simulated with the real scheduler)
* **Handback refresh wait (blocker found in review).** PR head (reuse for any arrival): 24 handback runs, **18 `halt_refresh_wait`**, 6 ok. Phase gate (and separately the boost rule): 18/18 ok, identical to 1.9.0.
* **Timeouts versus the 10 s margin.** Slow *successful* responses up to the 20 s HTTP timeout never publish offline (availability is evaluated only when idle or after a failure) although the success stamp can land past 300 s (gap 309 s at 19 s). That is **not** a 300 s guarantee: a concurrent MQTT-thread diagnostics publish mid-flight is not modelled. A connection reset is absorbed by the 5 s retry. **Connect (5 s) and read (15 s) timeouts are not tolerated**: one offline publication, 15–25 s offline, recovered by the next attempt (fail closed); today's 180 s cadence rides the same fault with no offline.
* **Failure tolerance over 8 seeds** (80 % reset / 12 % connect / 8 % read timeouts, 15 ms median post-stamp work), offline publications and offline seconds per 48 h: 1.5 % failure: today 0.5 / 3 s, poll_interval 300 8.9 / 56 s, **this PR 1.6 / 23 s**; 12.8 %: today 12.5 / 339 s, poll_interval 300 56.8 / 1,421 s, **this PR 28.8 / 725 s**. This PR is **less tolerant than today** (it removed the second poll) and more than one request per cycle. Observed at 180 s: 0 transport failures in 490+ requests. `OFFLINE_SAFETY_MARGIN_S` trades it against budget: idle 419 / 433 / 453 requests per day at margin 10 / 15 / 22 s, with 12.8 % failure offline 725 / 449 / 114 s.
* 48 h composite (failed refresh, 12.8 % transport failure, 12 min outage, HA restart, native pre-emption, quota window, missing demand): 0 stale cycles and 0 unexplained offline publications outside the injected windows, identical backoff and fail-closed commands as today; a handback pending across an HA restart completes after start; missing demand reverts to the legacy cadence.

## 7. Limits of this evidence (NOT_RUN / unmodelled)
Docker e2e and any physical qualification were **not** run. The simulator models the cloud, latency and jitter, Package 19's template/translation/handback timing, and a heater with simple physics; it does not model concurrent MQTT-thread publishes, the Supervisor, or real post-stamp work (unmeasured; 60 ms of it breaks one-request-per-cycle but not this PR). The vendor limit may not scale with request count at all (issue #17).

## 8. Supervised commissioning, rollback and the restart safety preflight
Merge ≠ release ≠ deploy: this PR does **not** bump the version; release separately (not combined with PR #24).
**Restart preflight — required before EVERY add-on restart, including enabling the option and any rollback; evaluate it at that moment, never assume the state from an earlier stage.** An add-on restart loses in-memory pending commands, starts the device offline until the first validated poll, and **HA's start-handback does not fire on an add-on restart**. Proceed only when all hold, read from HA/diagnostics now:
1. `input_boolean.ems_hws_ownership_active` is **off**. If it is on: do not restart; let the normal handback finish (EMHASS deselects within minutes on every observed boost) or follow the Package 19 handback runbook. If handback cannot complete (quota, outage), leave the option as it is: it does not weaken the handback path.
2. `script.hws_thermowatt_handback` is off, the translation automation is not mid-run (act 90–260 s after a cycle start) and `sensor.p_deferrable0_state` is off.
3. No pending command: `sensor.outside_hws_hws_command_status` is `idle`/`confirmed` and not inside a 60 s confirmation window.
4. Native baseline intact: `water_heater.hws_boiler_hws` is `Manual`, its setpoint equals `input_number.ems_hws_captured_baseline_setpoint_c` (or no baseline is captured) and heating is not an owned boost.
5. `poll_status` ok, consecutive failures 0, no quota backoff, `last_successful_poll` fresh.
After the restart: availability back online within 6 min, ownership still off, no unexpected commands, request rate back to 24–30/h (option off) or per §5 (option on). An option change in Supervisor restarts the add-on: treat it as the same operation.
**Commissioning:** (1) install with the option off, 1 h at 24–30 requests/h; (2) preflight, option on, restart, `demand_refresh.reused > 0` after 12 min; (3) ≥ 48 h with **ownership OFF**: ≤ 430 requests per full UTC day, source age ≤ 120 s at every cycle outside quota windows (max ≤ 100 s at the translation event), zero unexplained offline publications and ≤ 5 offline events/48 h overall, transport failures ≤ 1.5 %, reuse:served ≥ 3:1, first-rejection count recorded; (4) only with separate approval, ownership ON for ≥ 3 boost days: every handback script run `ok` (script traces show no refresh-wait timeout), all commands confirmed, telemetry age at the translation event while owned ≤ 60 s, requests/day ≤ idle + 5 × commands + 10 %.
**Rollback triggers:** one stale cycle outside a quota window, a handback halted at its refresh wait, a command not confirmed, an unexplained offline, > 460 requests on an idle day, reuse stuck at 0. Rollback = **preflight, then** option false + restart (restores the 1.9.0 policy exactly; the HA store offers only higher versions, so a code rollback is a roll-forward release). Do not roll back by restarting during an owned boost or a pending handback.
